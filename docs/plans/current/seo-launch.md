# План: SEO к запуску

Задача: довести сайт до состояния, в котором его можно отдавать в Яндекс.Вебмастер
и Google Search Console, и закрыть найденные дыры в индексации, разметке и
скорости.

Основание — прогон четырёх скиллов (`seo-onpage`, `seo-keyword`, `seo-aeo-geo`,
`performance-optimization`) по коду на коммите `22fe445` + ревью плана отдельным
агентом против доков Next 16.3.3 в `node_modules/next/dist/docs/`.

## Контекст, который определяет приоритеты

Города и распределение объявлений смотреть в данных, а не в этом файле:

```bash
cat seed_real/cities.csv
tail -n +2 seed_real/listings.csv | cut -d, -f2 | sort | uniq -c
```

На момент написания: два города — Краснодар и Яблоновский (пригород, но это
Республика Адыгея, другой субъект), причём **большинство объявлений в
Яблоновском**. Категорий: 10 корневых, 47 подкатегорий
(`src/lib/seed/categories.ts`), объявлений ~60.

Выводы, на которых стоит план:

1. **Сервис локальный** — стратегия строится на агломерацию, не на страну.
2. **Страниц в индексе будет порядка сотни.** Подкатегория существует только
   при ≥1 активном объявлении, большинство подкатегорийных адресов сейчас 404.
3. **Главный риск — не оптимизация, а тонкость.** На таком объёме Яндекс
   склонен вешать фильтр за малополезный контент. Наполнение страниц смыслом
   важнее микроправок тегов.

## Вопросы владельцу (нужны до этапа 4, не блокируют этапы 0–3)

**В1. Регион в Яндекс.Вебмастере.** Региональность одна на сайт, а инвентарь
раскидан по двум субъектам федерации, и большая его часть — в Яблоновском.
Варианты: Краснодар (крупнейший спрос), Яблоновский (большинство предложения),
не задавать вовсе. Учесть: назначение региона требует подтверждения (Яндекс
Бизнес либо страница с адресом и контактами) — физического адреса у сервиса
нет, может не пройти; тогда вопрос снимается сам.

**В2. Wordstat по «прокат/аренда».** Прогнать 10 корневых категорий по региону
Краснодар в трёх формулировках: «аренда X краснодар», «прокат X краснодар»,
«X напрокат краснодар». Без чисел заголовки не трогаем.

**В3. Кто рисует `public/og-default.png` (1200×630)?** Могу сгенерировать
плейсхолдер из бренд-ассетов `theme/brand/`; без файла пункт 1.1 неполон.

## Этап 0 — до деплоя, блокирующее

**0.1. Проверить `NEXTAUTH_URL` на сервере.** Из неё строятся все canonical
(`src/lib/site-config.ts`), sitemap и ссылка на sitemap в robots. Значение —
ровно `https://<домен>`: без завершающего слэша, без `www` (Caddyfile редиректит
`www` на голый домен). Правка только `.env`.

**0.2. Подключить IndexNow.** `src/lib/indexnow.ts` написан и покрыт тестами,
но `pingIndexNow()` не вызывается ниоткуда. Подключаем:

- вызовы в Server Actions владельца (`src/server/actions/owner.ts`):
  публикация, снятие с публикации и **редактирование** (смена title меняет slug
  и, значит, URL карточки);
- строго через `after()` из `next/server`: `pingIndexNow` — это `await fetch`
  с таймаутом 5 с, прямой вызов повесил бы Server Action на внешний сервис;
- файл ключа: `public/<INDEXNOW_KEY>.txt` (см. DEPLOY.md §8.1). `public/`
  запекается в образ — **требует пересборки при заведении ключа**;
- обновить: `docs/seo.md`, `docs/DEPLOY.md` §8.1, `docs/environment.md`
  (строки «модуль не подключён»), `docs/architecture.md` (Current limitations).

**0.3. Завести счётчик Метрики**, `YANDEX_METRIKA_ID` в `.env` до подачи в
Вебмастер: привязанная Метрика ускоряет первичное индексирование.

**0.4. Подтверждение прав — через DNS, не HTML-файлом** (файл в `public/`
потребовал бы пересборки образа). Google: property типа «Домен», DNS TXT.
Яндекс: DNS-запись. Кода не касается.

Ручные шаги после деплоя дописать в DEPLOY.md §8.3: регион (по ответу на В1),
привязка Метрики, submit sitemap в обоих сервисах.

## Этап 1 — техническая база индексации

**1.1. Open Graph.** Сейчас `openGraph` не задаёт ни одна страница,
`metadataBase` не задан, `seo.ogDefault` в `theme/seo.ts` ссылается на
несуществующий файл.

- `metadataBase` в корневом layout — из `getEnv().NEXTAUTH_URL`, **не** из
  `siteConfig.url`: тот читает сырой `process.env` с фолбэком на localhost, а
  `new URL()` на кривом значении уронит загрузку модуля;
- дефолтный OG (title, description, siteName, locale, image) в корневом layout;
- на карточке товара `openGraph.images` = первое фото объявления;
- `public/og-default.png` — см. В3;
- после правки посмотреть вывод `next build`: если какой-то роут внезапно
  пререндерился (`○`), в его OG уедет localhost — `NEXTAUTH_URL` в билд-этап
  Dockerfile не пробрасывается.

Ловушка `metadata.icons` (комментарий в `src/app/layout.tsx`) ветки `openGraph`
не касается — проверено по `resolve-metadata.js`, слияние иконок завязано
только на поле `icons`. Само поле по-прежнему не трогать.

**1.2. Canonical на главной.** `(public)/page.tsx` не задаёт
`alternates.canonical` — ссылки с `utm_*` из VK и рассылок станут отдельными
URL. Добавить self-canonical.

**1.3. `Clean-param` в robots.txt.** Фильтры каталога дают уникальный URL на
каждую комбинацию (`price_min`, `price_max`, `deposit`, `handover`, `verified`,
`category`, `from`, `to`, `view`, `sort`, `q` — см.
`src/lib/catalog/filters.ts`), плюс рекламные метки `utm_*`, `yclid`, `gclid` —
их в список тоже. `page` не включать: он меняет контент.

Реализация: Next 16.3 поддерживает нестандартные директивы через поле `other`
у правила в `MetadataRoute.Robots` (доки robots.md, «Non-standard directives»).
Добавить `other: { "Clean-param": [...] }` **в существующее правило
`userAgent: "*"`** — Route Handler не нужен, `src/app/robots.ts` остаётся.
Отдельную секцию `User-agent: Yandex` не заводить: Яндекс взял бы только её и
потерял `Disallow: /admin`, `/banned`, `/api/`.

**1.4. Self-canonical для пагинации.** Категория, подкатегория и витрина города
ставят canonical на адрес без параметров — со страницы 2 это сообщает «этой
страницы нет». Все три страницы `force-dynamic`, `searchParams` в
`generateMetadata` доступен — ломать нечего. Правила:

- в canonical попадает **только** `page`, никакие другие параметры — иначе
  self-canonical появится у каждой комбинации фильтров и обесценит 1.3;
- `page=1` = canonical без параметра;
- значение брать через `parseFilters()`, не из сырой строки;
- в `[sub]/page.tsx` роут двойной: в ветке карточки товара приходят
  `from`/`to` от виджета брони — им в canonical нельзя, там правка не нужна.

**1.5. `/login` и `/reset` — метаданные.** Сейчас ни title, ни description, ни
canonical — обе страницы наследуют дефолт корневого layout и уходят в индекс
**с тем же title и description, что у главной**. Дублирующиеся тонкие страницы —
ровно сценарий «малополезного контента». Дать каждой свой title, короткий
description и canonical. `noindex` не ставим: страница входа в выдаче по
запросу «инрента вход» полезна.

**1.6. `/u/{id}` — включить в sitemap** профили с ≥1 активным объявлением
(новый запрос в `src/server/catalog.ts`), остальным — `noindex, follow` в
`generateMetadata`. Так профили работают внутренними ссылками на карточки, а
тонкие — не индексируются.

## Этап 2 — разметка и смысл на страницах

**2.1. Недостающие типы JSON-LD** (`src/lib/jsonld.ts`):

- `Organization` на главной;
- `WebSite` + `SearchAction` на главной — честная оговорка: sitelinks searchbox
  Google больше не показывает, ценность — Яндекс и AI-извлечение;
- `ItemList` на категорийных страницах и витрине города;
- `FAQPage` — только вместе с 2.2; rich-сниппет FAQ Google маркетплейсу не
  даст (с 2023 — только авторитетным источникам), ценность — Яндекс и AEO.

`Product` дополнить `areaServed` (город объявления) и `itemCondition`.
Рейтинги не выдумывать — их в системе нет.

**2.2. Блок вопросов на категорийных страницах.** Сейчас из текста там одна
строка статистики. Добавить 3–5 вопросов про залог, бронь, передачу вещи —
текст из реальных правил сервиса. Тексты — в `theme/content.ts` (конвенция
проекта), разметка `FAQPage`. Формат под AEO: прямой ответ в первых двух
предложениях, заголовки-вопросы.

**2.3. Цены как цитируемые данные.** `getCategoryStats` уже считает минимум,
максимум и средний залог. Вывести явной фразой «средняя цена аренды
<категории> <в городе страницы> — N ₽/сутки, залог от M ₽» — город берётся из
страницы, не хардкодится Краснодар. Оригинальные данные — то, что цитируют и
Яндекс, и AI-поисковики.

**2.4. `llms.txt`** — Route Handler в `src/app/llms.txt/route.ts` (список
категорий из базы; обычные GET-хендлеры в Next 16 динамические по умолчанию,
`force-dynamic` не нужен). Описание сервиса — из `theme/content.ts`.
robots.txt уже разрешает всех AI-агентов, отдельно ничего открывать не надо.

## Этап 3 — скорость

**3.0. Замер до правок.** Lighthouse на проде: главная, витрина города,
карточка. Всё ниже — гипотезы из чтения кода; после каждой правки перемер.

**3.1. Дедуп запросов через `cache()`.** Самый крупный дешёвый выигрыш по
TTFB: `resolve()` на каждой каталожной странице выполняется дважды — из
`generateMetadata` и из компонента. На карточке товара это удвоенные
`getCityBySlug` + `getActiveListingById` + `getCategoryById` + `getSellerById`.
Плюс `getAllCategories()` зовётся по 2–3 раза за рендер и не обёрнута — в
отличие от `getActiveCities`, которая уже в `cache()` с комментарием зачем.
Обернуть `getAllCategories` и резолверы страниц. Кросс-запросный кэш
(`unstable_cache` устарел, `use cache` требует миграции на `cacheComponents`,
несовместимой с `force-dynamic`) — **не в этой задаче**; если понадобится,
отдельным заходом.

**3.2. LCP на категорийных страницах.** Первые карточки сетки грузят фото
лениво (`ListingCard.tsx`, `<Image>` без пометок). `priority` в Next 16
**deprecated** → на первые 2–4 карточки `loading="eager"`,
`fetchPriority="high"` — максимум на одну первую (LCP-элемент зависит от
вьюпорта, преload нескольких конкурирует за канал — предупреждение из доков
image.md). Заодно в `Gallery.tsx` заменить устаревший `priority` на `preload`.

**3.3. Шрифты.** Четыре семейства через `next/font` (самохост, третьей стороны
нет). JetBrains Mono с кириллицей подключён ради капсов 10–11 px — оценить
отказ от него после замера 3.0, не раньше.

**3.4. `react-icons`** (4 иконки провайдеров) — импорты подпутями тришейкятся,
ожидаемый выигрыш ~0. Не трогать без показаний от замера.

## Этап 4 — запросы и контент (после ответов В1–В2)

**4.1. «Прокат» против «аренды» в title** категорийных страниц — по числам из
В2. У велосипедов, самокатов, костюмов «прокат» почти наверняка частотнее;
у инструмента — наоборот. Без чисел не трогаем. Само слово «прокат» больше не
ограничено: после смены позиционирования (вещи размещают и прокатные сервисы)
оно легально в текстах, и «аренда и прокат» уже стоит в `defaultTitle` — числа
из В2 нужны только для порядка слов в категорийных title.

**4.2. Кластеры запросов** из таксономии:

| Кластер | Интент | Целевая страница | Есть? |
|---|---|---|---|
| «аренда/прокат <категория> <город>» | транзакционный | категория | да |
| «аренда <вещь> <город>» | транзакционный | подкатегория, карточка | частично |
| «сколько стоит аренда <категория>» | коммерческий | категория + блок 2.3 | после 2.3 |
| «как сдать вещи в аренду» | информационный | — | **осознанно не закрываем** |

**4.3. Посадочной для владельцев не будет — решение владельца.** Предложение
приходит в основном от прокатных сервисов, которых владелец зовёт напрямую;
отдельная страница «сдай вещи в аренду» не нужна. Информационный кластер «как
сдать в аренду» при этом остаётся незакрытым — это осознанный отказ, не
пробел; вернуться можно, если частники станут заметным источником предложения.

## Чего этот план осознанно не делает

- **Не чинит `permanentRedirect`** (200 вместо 301 — см. BACKLOG, раздел про
  канонизацию). Неканоничным адресам в норме взяться неоткуда, canonical
  проставлен верно.
- **Не разбивает sitemap на индекс** — актуально после ~10k объявлений.
- **Не трогает `noindex` на `/search`** — верно сделано и обосновано в seo.md.
- **Не трогает пустой `alt` у миниатюр галереи** — декоративные.
- **Не заводит `hreflang`** — язык один.
- **Не заводит посадочную для владельцев** — отказ, а не откладывание; см. 4.3.
- **Не делает кросс-запросный кэш справочников** — см. 3.1.
- **Не делает CRO** — до трафика нечего оптимизировать.

## Порядок и проверки

Этапы 0–2 — до подачи в вебмастеры, одним деплоем (0.2 и 1.1 всё равно требуют
пересборки образа: файл ключа и og-картинка живут в `public/`). Этап 3 — после
замера на проде. Этап 4 — после ответов В1–В2.

Слои: `theme` (`seo.ts`, `content.ts`), `src/app` (layout, robots, страницы
каталога и auth, `llms.txt/route.ts`, sitemap), `src/lib` (jsonld),
`src/server` (catalog: `cache()` + запрос продавцов для sitemap),
`src/server/actions` (owner: вызовы IndexNow через `after()`),
`src/components` (ListingCard, Gallery, блок FAQ), `docs` (seo.md, DEPLOY.md,
environment.md, architecture.md, BACKLOG.md).

Тесты (`tests/seo/` уже есть): canonical главной, OG-теги, новые типы JSON-LD,
`Clean-param` в robots, метаданные `/login`/`/reset`, продавцы в sitemap,
вызов IndexNow из actions. Каждый тест обязан падать до правки.

После: `pnpm test`, `pnpm exec next typegen && pnpm exec tsc --noEmit`.
`pnpm check-theme` не нужен — `theme/tokens.css` не затрагивается.
