## Задача 1: чат без реалтайма

### Чего задача сознательно не делает

Реалтайм, таблица `notifications`, вложения, «печатает…», статусы прочтения на
отдельном сообщении, редактирование и удаление сообщений, жалобы и модерация
переписки, письмо на почту о новом сообщении, блокировка пользователя.

Следствие, которое надо принять осознанно: **человек узнаёт о новом сообщении,
только когда сам зайдёт на сайт.** Других каналов у задачи 1 нет. Это и есть
основная причина существования задачи 2.

### Схема БД

`drizzle/schema.ts` + миграция через `pnpm db:generate`.

**`chat_threads`**

| Колонка | Тип | Комментарий |
|---|---|---|
| `id` | text pk | ULID через `newId()` |
| `listing_id` | text → `listings` cascade | |
| `customer_user_id` | text → `users` cascade | арендатор |
| `owner_user_id` | text → `users` cascade | денормализован из `listings.owner_user_id` — ровно по той же причине, что в `booking_requests`: индекс «мои переписки» без join. Владелец неизменен, рассинхрона нет |
| `last_message_at` | timestamp | сортировка списка диалогов |
| `owner_last_read_message_id` | text null | ULID-курсор |
| `customer_last_read_message_id` | text null | ULID-курсор |
| `created_at` | timestamp | |

- `UNIQUE (listing_id, customer_user_id)`
- `INDEX (owner_user_id, last_message_at DESC)`
- `INDEX (customer_user_id, last_message_at DESC)`

**`chat_messages`**

| Колонка | Тип | Комментарий |
|---|---|---|
| `id` | text pk | ULID — лексикографически сортируется по времени |
| `thread_id` | text → `chat_threads` cascade | |
| `sender_user_id` | text → `users` cascade | |
| `body` | text | предел длины — в zod, не в БД |
| `created_at` | timestamp | |

- `INDEX (thread_id, id DESC)` — курсорная пагинация
- `INDEX (sender_user_id)` — иначе каскад при удалении пользователя пойдёт
  сиквеншл-сканом. Хард-удаления юзеров сейчас нет (бан мягкий), но индекс дешёвый.

**Превью последнего сообщения не денормализуется.** Берётся `LATERAL`-джойном к
`chat_messages`. Отдельная колонка под превью породила бы гонку записи и на текущих
объёмах ничего не экономит. `last_message_at` при этом остаётся — по нему идёт
сортировка, и без колонки в индексе сортировать нечем.

### Точка входа

Кнопка «Написать» уже есть в `OwnerCard.tsx:52` и ведёт на `/u/{id}`.
Перенаправляется на чат.

- **Аноним** — открывается `LoginTrigger` с `redirectTo`, как у «Сдать» в шапке
  и у модалки входа в `BookingWidget`. Не редирект middleware: он даёт вспышку интерфейса.
- **Владелец на своём объявлении** — кнопки нет.
- **Профиль `/u/[id]`** — кнопки «Написать» там нет. Тред без объявления не заводится,
  а выбор объявления в профиле — лишний экран ради редкого сценария.

### Правила доступа

Проверяются **в самой мутации** — Server Action доступен по сети напрямую.
Порядок и стиль — как в `createBookingRequest` (`src/server/actions/booking.ts:34-52`).

1. Залогинен.
2. Не забанен (`session.user.bannedAt`).
3. Вход проходит zod-схему; `body` после `trim` не пуст, длина в пределах.
4. Не превышен лимит.
5. Новый тред — только к объявлению в статусе `active`.
6. Владелец не заводит тред к своему объявлению.
7. В существующий тред пишут только двое его участников.

**Мёртвое объявление и забаненный собеседник:** читать можно всегда, писать нельзя.
Если объявление ушло в `hidden`/`archived` или собеседника забанили — тред открывается,
история видна, композер заменён пояснением. Витрина забаненного отдаёт 404, поэтому
ссылка на профиль из шапки треда в этом случае не рисуется.

**Гонка при создании треда:** `INSERT ... ON CONFLICT DO NOTHING` по
`UNIQUE (listing_id, customer_user_id)`, затем `SELECT`.

### Непрочитанное

Курсор — `*_last_read_message_id` в ULID, одна основа сравнения с индексом
`(thread_id, id DESC)`. Timestamp не годится: с ULID его не сравнить.

- Непрочитанное в треде: `WHERE thread_id = ? AND id > cursor AND sender_user_id <> me`.
- Бейдж в навигации: сумма по своим тредам.

**Список диалогов пишется как `UNION ALL` двух ветвей** — «где я владелец» и «где я
арендатор», с `LIMIT` в каждой. Наивный `WHERE owner_id = me OR customer_id = me`
даст BitmapOr и сортировку всего набора, оба индекса при этом бесполезны.

### Антиспам

Два новых бакета в `src/lib/rate-limit.ts` (плюс union `LimitKind`, плюс
`tests/lib/rate-limit.test.ts`, плюс таблица в `docs/auth.md`):

- `chat_message` — 60 сообщений в час, `gapMs: 0`. **Отклонение от плана:** сначала
  закладывалась пауза 1–2 с, но она ничего не защищает сверх часового потолка, зато
  режет живую переписку и двойные отправки. Взят прецедент `login` — «паузы нет,
  работает счётчик».
- `chat_thread` — 10 новых тредов в час, от бота, рассылающего рекламу сотне
  владельцев: потолок сообщений он бы прошёл, отправляя по одному в каждый тред.

Помнить: лимитер в памяти процесса, `MAX_KEYS = 10_000` с FIFO-вытеснением. Чат
меняет профиль нагрузки на него сильнее, чем всё остальное вместе.

### Раскладка

Тред — первый экран в проекте с прижатым вниз композером и внутренним скроллом ленты.
Против него работают: скролл на `<html>` (`globals.css:11,29`), плавающий таб-бар
(`--tabbar-h`), sticky-панель на `--header-total`.

Поэтому **тред живёт вне `AccountShell`**, со своим layout. Иначе на каждой переписке
рисуется обложка-герой и сайдбар, а композер не фиксируется.

Список диалогов — внутри личной зоны, пунктом навигации. Значит `/chat` вносится в
`buildAccountNav`: без этого `currentItem` окажется `undefined`, и страница отрисуется
без заголовка и без мобильной кнопки «назад».

Иконка заводится дважды — в `accountNav.ts` и в словаре `ICONS` внутри клиентского
`AccountShell.tsx`. Иконки через границу RSC не ездят, дублирование вынужденное.

Метаданные как у остальных личных страниц: `robots: { index: false }`,
`export const dynamic = "force-dynamic"`. Проверить, что `sitemap.ts` чат не подхватит.

Темы и адаптив обязательны, цвета только через токены `theme/tokens.css`.

### Что переживёт задачу 2

Ради этого и делится работа. Решения, принятые сейчас, чтобы потом не переписывать:

1. **Отправка сообщения — одна транзакция:** вставка `chat_messages` + `UPDATE
   chat_threads.last_message_at`. В задаче 2 туда же добавится `pg_notify`. Если
   сделать двумя запросами — мутацию придётся переписывать.
2. **Server Action возвращает созданное сообщение целиком** (`id`, `createdAt`,
   `senderUserId`, `body`), а не `{ ok: true }`. В задаче 2 этим дедуплицируется эхо
   сокета против ответа экшена.
3. **Лента — клиентский компонент, засеянный пропсами из SSR.** Не серверный компонент
   с `router.refresh()`: он выбрасывается целиком при подключении сокета. Вставка по
   `id` идемпотентна — тогда любой порядок прихода даёт один результат.
4. **«Загрузить старые» — кнопкой через состояние компонента, не через `?before=` в URL.**
   URL-вариант в задаче 2 пришлось бы снимать.
5. **Схема не меняется.** Тред по паре «объявление + арендатор», курсор по ULID,
   `last_message_at` для сортировки.

Отдельно: `revalidatePath` для чата почти бесполезен — страницы `force-dynamic`, а
собеседнику он ничего не обновит. Строить на нём «доставку» в задаче 1 нельзя.

### Отклонения от плана, названные вслух

- **Чат живёт внутри `(me)`/`AccountShell`, а не отдельной группой роутов.**
  План требовал `src/app/(app)/chat/*` со своим layout, чтобы на переписке не
  рисовались обложка и герой. Решение изменено по ходу задачи: заказчик выбрал
  раскладку «сайдбар кабинета + две колонки чата» и попросил вернуть обложку,
  как на остальных экранах. Композер прижат снизу через `sticky`, а не
  фиксированной высотой, поэтому смена каркаса ему не помешала. Побочный эффект,
  который пришлось убрать отдельно: кнопка «назад» рисовалась дважды — своя у
  шапки треда и общая у `AccountShell`.
- **Список диалогов собирается двумя выборками со слиянием в приложении,
  а не `UNION ALL` в SQL.** Форма выполнения та же (два индексных прохода без
  общей сортировки), но запросы остаются типизированными Drizzle.
- **Вместо второго демо-аккаунта в `scripts/seed.ts` заведена dev-ручка
  `POST /api/dev/chat`** — по образцу `POST /api/dev/booking`, с тем же
  kill-switch по `NODE_ENV`. Сид проверяет данные, а ручка проверяет флоу с
  двух сторон, включая отказы; для чата это оказалось нужнее.
- **`chat_message` получил `gapMs: 0`** вместо заложенных 1–2 с: пауза ничего
  не защищает сверх часового потолка, зато режет живую переписку и двойные
  отправки. Взят прецедент `login` — «паузы нет, работает счётчик».
- **Добавлен третий бакет `chat_read`.** В плане его не было. Закрывает
  `markThreadRead` и `fetchOlderMessages`: они вызываются с клиента и стоят
  несколько запросов каждый, а лимита у них не было вовсе.
- **ULID-монотонность: решение принято.** Отложенный планом выбор сделан в
  пользу `monotonicFactory` — `newSortableId()` в `src/lib/id.ts` для id
  сообщений. Гарантия держится в пределах процесса; при нескольких инстансах
  вырождается до обычного ULID, но расходятся тогда только сообщения одной
  миллисекунды в одном треде.

### Отклонения от паттернов проекта, названные вслух

- **Чат не пишет в `events`.** Все существующие мутации пишут туда строку в той же
  транзакции. Для чата это объём без пользы: `getCabinetSummary` такую статистику не
  читает. Решение сознательное.
- **`listing_id ... cascade`:** жёсткого удаления объявлений в коде нет
  (`setListingStatus` только меняет статус). Если появится — вместе с объявлением
  исчезнет вся переписка.
- **ULID не монотонный внутри миллисекунды.** `newId()` это `ulid()`, не
  `monotonicFactory`. Проект допущение уже принял (`docs/architecture.md:122`). Для
  курсора теоретически даёт пропуск на границе окна; задача 2 будет дочитывать дельту
  тем же курсором. Либо `monotonicFactory` для сообщений, либо `created_at` вторым
  ключом сортировки — решить при реализации.

### Отложено внутри задачи

**Доработка внешнего вида переписки.** Базовая раскладка сделана и работает
(две колонки на десктопе, одна на мобиле, композер прилипает снизу, обложка и
герой как на остальных экранах кабинета), но по виду это черновик: пузыри,
плотность, разделители по дням, поведение длинных сообщений. Решено доводить
отдельным проходом, когда в переписке будут настоящие данные.

## Задача 2: доставка по вебсокетам (эскиз)

Не реализуется в этой задаче. Записано, чтобы задача 1 не загнала в угол.

**Почему отдельный процесс.** Route handlers Next не апгрейдят соединение
(`node_modules/next/dist/docs/01-app/02-guides/backend-for-frontend.md:927`), а
кастомный сервер несовместим с `output: "standalone"`
(`.../custom-server.md`), на котором собран весь runner-слой `Dockerfile`.

**Топология.** Контейнер `realtime` (Node + `ws`) рядом с `app` в `docker-compose.yml`,
Caddy маршрутизирует `/ws*` на него. Сборка — esbuild-бандлом, как `migrate.cjs`,
поэтому переиспользует `@/`-алиасы, схему Drizzle и код сессий.

**Поток.** Server Action пишет в БД и делает `pg_notify` в той же транзакции (Postgres
доставляет только при коммите). `realtime` сидит на `LISTEN` — **отдельное соединение
с Postgres, не из пула Drizzle**. Находит сокеты по `userId`, пушит.

**Наверх по HTTP, вниз по сокету.** Отправка остаётся Server Action'ом: иначе в
`realtime` придётся продублировать все проверки прав и валидацию. Браузер по сокету
шлёт только heartbeat.

**Клиент.** Хранилище на `useSyncExternalStore` — не Redux: срез состояния один,
зависимостей ноль, подписки селекторами не дают перерисовывать шапку на каждое
сообщение. Засевается данными из SSR. При обрыве дочитывает дельту по курсору.

**Плюс таблица `notifications`** — `user_id` это **получатель**, с каскадом. Не
переиспользовать `events`: там `userId` это тот, кто совершил действие (у
`submit_request` — арендатор, а уведомлять надо владельца), и `on delete set null`,
правильный для аналитики и неправильный для доставки.

**Известные засады.**
- `pg_notify` — предел полезной нагрузки ~8 КБ. Слать `{userId, id}`, тело читать из БД.
- `perMessageDeflate` в `ws` включён по умолчанию и держит zlib-контекст на каждое
  соединение. Выключить, иначе память кончится на первых тысячах.
- Имя session-cookie зависит от схемы URL (`sessionCookieName()` в
  `src/lib/auth/session.ts`), а `realtime` живёт без `src/lib/env.ts`.
- Клиент **молча игнорирует незнакомые типы событий**: при деплое в открытых вкладках
  остаётся старый JS.
- «Заявка протухла» в реальном времени не придёт: крона нет, протухание ленивое.
