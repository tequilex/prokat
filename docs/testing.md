# Тесты и проверки

## Чем проверяется код

| Команда | Что делает | Состояние |
|---|---|---|
| `pnpm test` | Vitest, один прогон | работает |
| `pnpm test:watch` | Vitest в watch-режиме | работает |
| `pnpm exec tsc --noEmit` | проверка типов по всему проекту | работает |
| `pnpm check-theme` | проверяет, что в `theme/tokens.css` есть все обязательные токены | работает |
| `pnpm lint` | — | **не работает**, см. ниже |

Перед коммитом осмысленный минимум — `pnpm test` и `pnpm exec tsc --noEmit`.
Если трогали `theme/tokens.css` — ещё и `pnpm check-theme`.

## Линтера в проекте нет

`pnpm lint` вызывает `next lint`, но конфигурации ESLint в репозитории не
существует (`.eslintrc*` и `eslint.config.*` отсутствуют). В Next 15.5 команда
объявлена deprecated и вместо проверки уходит в **интерактивный визард**
«How would you like to configure ESLint?», где и виснет в ожидании ввода.

Практический вывод: не запускать `pnpm lint` в скриптах и в CI — процесс
зависнет. Роль статической проверки выполняет `tsc --noEmit` со `strict: true`.

`NEEDS REVIEW`: настроить ESLint через `eslint.config.js` или убрать скрипт
`lint` из `package.json`. По коду нельзя понять, был линтер потерян при
миграции или от него отказались сознательно.

## Устройство тестов

- Runner — **Vitest**, окружение `jsdom`, конфиг `vitest.config.ts`.
- Тесты лежат **только в `tests/**`** и подхватываются по маске
  `tests/**/*.test.ts(x)`. Файлы рядом с исходниками не собираются — если
  положить тест в `src/`, он просто не запустится.
- Структура `tests/` зеркалит `src/`.
- Импорты внутри тестов — через те же псевдонимы, что и в коде: `@/`, `@theme/`,
  `@db/`. Они продублированы в `vitest.config.ts`.
- Общий setup — `tests/setup.ts`, там подключается `@testing-library/jest-dom`.
- JSX задан явно (`esbuild: { jsx: "automatic" }`): Vitest идёт через esbuild и
  не читает `jsx: "preserve"` из `tsconfig.json`, который нужен Next.

## Что покрыто

Живого Postgres тесты **не требуют** — это принципиальное свойство набора.

| Область | Как тестируется |
|---|---|
| Доменная логика | чистые функции: занятость, статусная машина, даты, фильтры, слаги, разбор пути объявления |
| Сценарии входа | `src/lib/auth/flows.ts` через порт `store.ts` — фейковая реализация в памяти (`tests/fixtures/auth-store.ts`) вместо базы |
| Токены, пароли, стоп-лист | напрямую |
| Схема БД | shape-тесты: проверяется наличие таблиц и колонок в `drizzle/schema.ts`, без подключения |
| Переменные окружения | `parseEnv` на наборах значений, включая production-ветку |
| Компоненты | Testing Library: рендер и поведение (шапка, поиск, формы, галерея, фильтры) |
| Загрузка файлов | route-хендлер с замоканными S3 и sharp; есть фикстуры-картинки в `tests/fixtures/images/` |
| SEO | JSON-LD и robots |

Именно ради тестируемости без базы auth-логика вынесена в чистые функции с
инъекцией зависимостей: Server Actions — тонкие обёртки, которые собирают
`store`, `sendMail` и лимиты, а вся логика лежит в `flows.ts`.

**Количество тестов здесь намеренно не указано** — оно меняется с каждой
задачей. Текущее значение выводит `pnpm test`.

## Как писать новый тест

1. Файл кладётся в `tests/`, путь повторяет расположение в `src/`.
2. Имя — `*.test.ts` или `*.test.tsx`.
3. Логику тестируем как чистую функцию. Если для этого нужна база — скорее
   всего, логику стоит вынести из Server Action в `src/lib/**`, как сделано с
   auth.
4. Внешние сервисы (S3, SMTP, fetch) мокаются. Для почты есть
   `__setTransportForTests`, для S3 — `_resetR2ClientForTests`.

## Ручные проверки

Автотесты не видят реальную БД, cookie, редиректы, письма и вёрстку. Для входа
по почте есть отдельный чеклист: [QA-email-auth.md](QA-email-auth.md).

Перед деплоем — предполётный список в [DEPLOY.md](DEPLOY.md).

## Локальные грабли

- **Перед `pnpm build` остановить dev-сервер**: у них общий каталог `.next`.
- **`.next/types` держит устаревшие типы удалённых роутов** после работы
  dev-сервера и даёт ложные ошибки `TS2307`. Лечится `rm -rf .next/types`.
