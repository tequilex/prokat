# prokat — вход и регистрация по почте с паролем

Дата: 2026-08-11
Статус: согласовано в брейнсторме, ожидает вычитки

## Контекст и цель

Сейчас в проект можно попасть только через OAuth: Яндекс ID (штатный провайдер Auth.js)
и VK ID (собственный OAuth 2.1 + PKCE в `src/lib/auth/oauth-vk.ts`). Человек без аккаунта
в этих сервисах — или не желающий ими светить — зарегистрироваться не может.

Цель: добавить третий способ входа — **почта + пароль** — не ломая два существующих.

## Ключевые решения

1. **Пароль, а не магик-линк.** Повторный вход мгновенный, без письма.
2. **Подтверждение почты обязательно до первого входа.** Незаподтверждённый аккаунт войти
   не может.
3. **Автосклейки с OAuth нет.** Совпадение почты — понятный отказ с подсказкой, каким
   способом входить. Привязка второго способа из профиля — отдельная задача, не здесь.
   Из VK-флоу при этом удаляется существующая склейка по e-mail (см. «Правка VK-флоу»).
4. **Сессию выдаём сами, database-стратегия остаётся.** Credentials-провайдер Auth.js не
   используется.
5. **Стоп-лист почтовых доменов** с проверкой на сервере; юзеру сообщается конкретная
   причина, но только после ввода почты.
6. **Без настроенного SMTP в проде скрыты регистрация и сброс**, форма входа остаётся —
   письма для проверки пароля не нужны, а прятать вход у тех, кто уже завёл пароль, нельзя.

Сознательно **не** делаем сейчас (YAGNI): экран «Способы входа» в профиле (задать пароль
для OAuth-аккаунта, привязать/отвязать провайдера), смену почты, магик-линк, OTP-коды,
двухфакторную аутентификацию, словарь скомпрометированных паролей, капчу.

## Почему не Credentials-провайдер Auth.js

`session.strategy` в проекте — `"database"` (`src/lib/auth/config.edge.ts`). Это значит,
что сессия — строка в таблице `sessions`, а cookie хранит только её токен. На этом стоит
весь проект: VK-флоу пишет сессию в БД напрямую (`upsertUserAndSession`), `session`-коллбэк
берёт поля из `user`, отданного адаптером, а бан действует мгновенно — достаточно удалить
строку сессии.

`CredentialsProvider` требует `strategy: "jwt"`. Переход на JWT означал бы переписывание
VK-флоу и `session`-коллбэка, а забаненный юзер продолжал бы работать до истечения токена.
Цена несопоставима с выгодой.

Поэтому вход по паролю повторяет уже работающий в проекте паттерн: проверили пароль →
вставили строку в `sessions` → поставили cookie. Тот же механизм, другая проверка на входе.

Отвергнутый третий вариант — Credentials-провайдер с ручной подменой cookie на
database-токен внутри коллбэков — опирается на недокументированное поведение беты
`next-auth` и ломается при обновлении.

## Данные

### Изменения схемы (`drizzle/schema.ts`)

**`users` — новая колонка:**

| поле | тип | смысл |
|---|---|---|
| `passwordHash` | `text`, nullable | argon2id-хэш. У OAuth-юзеров NULL |

Отдельная таблица не нужна: связь строго 1:1. Существующая колонка `emailVerified`
(`timestamp`, сейчас всегда NULL) начинает использоваться по назначению — но **только для
password-аккаунтов**. У OAuth-юзеров она остаётся NULL навсегда: ни VK-флоу, ни
`DrizzleAdapter` её не проставляют, бэкфила не делаем. Поэтому проверять `emailVerified` в
общих гардах нельзя — это признак «password-аккаунт подтверждён», а не «аккаунт живой».

**`email_tokens` — новая таблица** (одноразовые ссылки из писем):

| поле | тип | смысл |
|---|---|---|
| `id` | `text` PK | ULID |
| `userId` | `text` → `users.id`, `on delete cascade` | чей токен |
| `purpose` | enum `verify` / `reset` | тип ссылки |
| `tokenHash` | `text`, uniq | sha256 от токена из письма |
| `expiresAt` | `timestamp` | 24 ч для `verify`, 1 ч для `reset` |
| `usedAt` | `timestamp`, nullable | штамп предъявления. Для `reset` повторный клик не сработает; для `verify` действует льготное окно 15 минут (см. «Подтверждение почты») |
| `createdAt` | `timestamp` | для чистки протухших |

Индекс по (`userId`, `purpose`) — нужен, чтобы гасить прежние токены при выпуске нового.

**Почему хэш, а не сам токен.** Строка из письма — это одноразовый пароль. Дамп БД (в том
числе бэкап, уезжающий в S3) с сырыми токенами даёт вход в чужие аккаунты. В письмо уходит
оригинал, в БД лежит sha256 — сверяем при клике. Соль не нужна: токен и так 32 случайных
байта, перебор бессмысленен.

**Почему не переиспользуем `verification_tokens`.** Это таблица Auth.js: составной ключ
(`identifier`, `token`), нет ни `purpose`, ни `usedAt`. Свои данные в ней конфликтуют с
адаптером, если позже появится магик-линк.

Миграция генерируется через `pnpm db:generate`, ломающих изменений нет: существующие юзеры
получают `password_hash = NULL`.

### Хэширование пароля

`argon2id` через `@node-rs/argon2` (нативный, без сборки из исходников). Параметры задаём
явно, не полагаясь на дефолты пакета: 19 МиБ памяти, 2 итерации, параллелизм 1
(рекомендация OWASP).

bcrypt отвергнут: лимит 72 байта на пароль (длинные парольные фразы молча обрезаются) и
слабее против перебора на GPU.

## Пользовательские флоу

### Регистрация

1. `/login`, форма «Почта и пароль» под кнопками провайдеров: почта, пароль, повтор пароля.
2. Сервер нормализует почту, проверяет стоп-лист доменов, правила пароля, лимиты.
3. Создаётся `users` с `emailVerified = NULL`, `passwordHash`, без `username`.
4. Выпускается токен `verify`, письмо уходит на почту.
5. Юзера **не** логиним — показываем «Письмо отправлено на a@ya.ru» и кнопку «Отправить ещё
   раз» (под лимитом).

### Подтверждение почты

Ссылка ведёт на `GET /api/auth/email/verify?token=…`:

1. Токен ищется по sha256, проверяется `purpose`, `expiresAt`, `usedAt`. Стоп-лист здесь
   **не** применяется (см. «Где проверяется» — иначе аккаунт стал бы невосстановимым).
2. `emailVerified = now()`, `usedAt = now()`.
3. Выдаётся сессия, редирект на `/welcome` выбирать `username` — тот же онбординг, что
   после OAuth (`requireAuthState` всё равно увёл бы туда).

Невалидный/протухший токен → `/login?error=verify_token_invalid` с предложением
зарегистрироваться заново или запросить письмо.

**Льготное окно на повторный клик.** Почтовые клиенты и корпоративные антивирусы ходят по
ссылкам сами, до человека. Поэтому переход по токену, погашенному менее 15 минут назад,
считается успехом и снова выдаёт сессию — иначе владелец почты стабильно получал бы
«ссылка недействительна» вместо входа. За пределами окна — обычный отказ.

Окно распространяется **только** на `verify`-токен, погашенный предъявлением. На `reset`
оно не действует: предъявленная ссылка сброса мертва сразу, иначе перехваченное письмо
оставалось бы рабочим ещё четверть часа после того, как пароль уже сменили. Токены,
отменённые выпуском нового письма, физически удаляются из таблицы (а не штампуются
`usedAt`) — иначе окно оживляло бы их и «отправить письмо ещё раз» переставало бы
обесценивать прежнюю ссылку. `usedAt` тем самым означает ровно одно: «предъявлен».

### Вход

1. Та же форма, режим «Войти».
2. Юзер ищется по нормализованной почте.
3. Юзера нет → фиктивная проверка argon2 (см. «Тайминги») и «Неверная почта или пароль».
4. Юзер есть, `passwordHash IS NULL`, но **есть строки в `accounts`** → «У этой почты вход
   через Яндекс или VK». Тот же осознанный компромисс по перечислению аккаунтов, что и на
   регистрации: нейтральный текст загнал бы человека в тупик. Если привязок тоже нет
   (аккаунт без способов входа) — ведём себя как при отсутствии юзера: войти в него всё
   равно нельзя, и подсказывать тут нечего.
5. Проверка `passwordHash`; несовпадение → «Неверная почта или пароль».
6. `emailVerified IS NULL` → отказ с предложением отправить письмо подтверждения повторно.
7. Успех → строка в `sessions` + cookie → редирект на `callbackUrl` (по умолчанию `/`).

`callbackUrl` пропускается через `safeCallback` (переезжает в `session.ts` из
`api/oauth/vk/callback/route.ts`) — только относительные пути, иначе открытый редирект.

Забаненный юзер входит штатно: сессия выдаётся, `requireAuthState` уводит на `/banned` —
так же, как с VK и Яндексом. Одна дорога вместо двух.

### Сброс пароля

1. `/login` → «Забыли пароль?» → форма с почтой.
2. Ответ всегда одинаковый: «Если такая почта зарегистрирована — письмо отправлено».
3. Токен `reset` (1 час) выпускается, только если юзер существует, у него есть
   `passwordHash` **и** `emailVerified IS NOT NULL`; прежние неиспользованные
   `reset`-токены этого юзера удаляются.
4. Ссылка ведёт на `/reset?token=…` — форма нового пароля; токен проверяется и при
   отрисовке страницы, и при отправке.
5. Успех: новый `passwordHash`, `usedAt`, **удаление всех строк `sessions` этого юзера** и
   всех его непогашенных `reset`-токенов, затем выдача новой сессии и редирект на `/`.

Удаление сессий обязательно: сброс — это в том числе реакция на угон, злоумышленник с
активной cookie должен потерять доступ немедленно.

У OAuth-юзера без `passwordHash` сброс не выпускает токен (ответ тот же, письма нет) —
иначе через «забыли пароль» можно было бы завести пароль к чужому OAuth-аккаунту.

Неподтверждённый аккаунт сброс тоже не получает — иначе после смены пароля человек оказался
бы в петле: сессию выдали, а следующий вход отклоняется по `emailVerified IS NULL`. Тупика
это не создаёт: забытый пароль до подтверждения лечится повторной регистрацией на ту же
почту (см. «Коллизии»), которая перезаписывает пароль и шлёт новое письмо.

### Коллизии почты с OAuth

**Дискриминатор — строки в `accounts`, а не `emailVerified`.** Это принципиально: у всех
существующих OAuth-юзеров `emailVerified IS NULL` (VK-флоу его не проставляет,
`oauth-vk.ts:183`; `DrizzleAdapter` для Яндекса тоже), и бэкфила не делаем. Правило «занят
неподтверждённый аккаунт → перезаписываем пароль», применённое к ним, дало бы захват
аккаунта: злоумышленник ставит свой `passwordHash` на чужой OAuth-аккаунт, жертве уходит
письмо «подтвердите регистрацию», она кликает — и пароль злоумышленника начинает работать.

Порядок проверок при регистрации, сверху вниз:

| условие | поведение |
|---|---|
| у юзера с этой почтой есть хоть одна строка в `accounts` | «Эта почта уже привязана ко входу через Яндекс/VK — войдите этим способом». Пароль не трогаем |
| привязок нет, `passwordHash IS NOT NULL`, `emailVerified IS NULL` | Брошенная регистрация: перезаписываем `passwordHash`, сносим прежние `verify`-токены, шлём новое письмо |
| привязок нет, `emailVerified IS NOT NULL` | «Эта почта уже зарегистрирована — войдите или восстановите пароль» |
| привязок нет, `passwordHash IS NULL` | Аккаунт без единого способа входа: проставляем `passwordHash`, шлём письмо — как строка про брошенную регистрацию |
| юзера нет | Обычная регистрация |

Предпоследняя строка выглядит экзотикой, но состояние массовое: `scripts/seed.ts` заводит
владельцев прямыми вставками в `users`, `/api/dev/login` — тоже, и оба не создают строк в
`accounts`. В проде оно достижимо иначе: `upsertUserAndSession` вставляет `users` и
`accounts` двумя запросами без транзакции (`oauth-vk.ts:183` и `:194`), и падение второй
вставки оставляет юзера-сироту. Раньше сироту молча подбирала склейка по e-mail — после её
удаления адрес оказался бы заперт навсегда. Присвоение безопасно: войти в такой аккаунт
сможет только тот, кто откроет письмо. Заодно вставки в VK-флоу оборачиваются в
транзакцию, чтобы сирот больше не появлялось.

Перезапись брошенной регистрации нужна, чтобы нельзя было «застолбить» чужой адрес: иначе
владелец почты никогда не зарегистрируется. Безопасно, потому что доступ получит только
тот, кто откроет письмо.

**Вход через OAuth, когда почта уже у password-юзера.** Яндекс: Auth.js отдаёт
`OAuthAccountNotLinked`, ловим на `/login` и показываем «У этой почты уже есть вход по
паролю». VK требует правки кода — см. ниже.

### Правка VK-флоу: убрать склейку по почте

`upsertUserAndSession` сейчас ищет юзера по e-mail и подшивает VK-аккаунт к найденному
(`oauth-vk.ts:172-179`). Это ровно та автосклейка, от которой мы отказались, и вместе с
password-аккаунтами она становится вектором захвата: аккаунт с подтверждённой почтой
`…@mail.ru` перехватывается входом через VK-шлюз с sub-провайдером `mail_ru`.

Ветка поиска по e-mail удаляется. Новое поведение: нет строки в `accounts` → создаём нового
юзера; если почта уже занята — редирект на `/login?error=email_taken` с тем же текстом «у
этой почты уже есть другой способ входа».

Уже склеенные аккаунты не затрагиваются: они находятся по строке в `accounts`, а не по
почте. Меняется только исход будущих коллизий.

VK-юзеры без почты получают заглушку `vk-<id>@vk.placeholder` и в коллизиях не участвуют —
такой домен в реальной почте не встречается.

## Стоп-лист почтовых доменов

**Зачем.** Требование законодательства РФ: поправки 2023 года в закон «Об информации»
(ФЗ-406 от 31.07.2023, в силе с 1 декабря 2023) ограничивают авторизацию пользователей на
российских сайтах — она должна опираться на российские системы (номер телефона РФ, ЕСИА,
ЕБС либо информационную систему, принадлежащую российскому лицу), а не на иностранные
почтовые сервисы. Точную формулировку и периметр применения стоит сверить с юристом; на
уровне кода мы даём механизм, а не юридическую оценку.

**Что из этого следует для состава списка.** Если мотив правовой, то одного `gmail.com`
мало — под ограничение попадают иностранные почтовые сервисы вообще. Стартовый список:
`gmail.com`, `googlemail.com`, `outlook.com`, `hotmail.com`, `live.com`, `msn.com`,
`yahoo.com`, `ymail.com`, `icloud.com`, `me.com`, `mac.com`, `aol.com`, `proton.me`,
`protonmail.com`, `gmx.com`, `zoho.com`. Список подлежит подтверждению владельцем проекта
перед реализацией.

**Чего список не касается.** Вход через Яндекс ID и VK ID не фильтруется по домену почты,
даже если провайдер вернул `@gmail.com`: авторизация в этом случае идёт через российскую
информационную систему, а почта — лишь атрибут профиля. Фильтр применяется только там, где
почта сама является каналом авторизации, то есть в собственной регистрации по паролю.

Список живёт в `src/lib/auth/blocked-email-domains.ts`. Расширяется двумя путями:

- правкой файла (требует пересборки);
- переменной `BLOCKED_EMAIL_DOMAINS=foo.com,bar.com` — значения добавляются к встроенному
  списку, домен закрывается рестартом контейнера.

Сравнение по домену в нижнем регистре после нормализации почты.

**Где проверяется: только при регистрации.** Ни подтверждение почты, ни вход, ни сброс
пароля стоп-листом не фильтруются. Причина: аккаунт к этому моменту уже существует, а
отсечение на этих шагах превращает добавление домена в список в способ отобрать у человека
аккаунт вместе с товарами и заявками — причём отказ на подтверждении делает аккаунт вообще
невосстановимым (войти нельзя — не подтверждён, подтвердить нельзя — домен в списке).

Следствие принято осознанно: домен, добавленный в список позже, закрывает только новые
регистрации, а уже заведённые аккаунты с таким доменом продолжают работать. Их разбор —
разовая операция над данными, а не поведение формы.

**Как сообщаем.** Заранее в форме ничего не пишем. Как только человек ушёл из поля почты,
форма дёргает Server Action `checkEmailDomain`, и под полем появляется красная строка
«Регистрация с почт gmail.com не поддерживается — войдите через Яндекс или VK» (домен
подставляется введённый). Список при этом не уезжает в браузерный бандл. Серверная проверка
при отправке формы остаётся источником истины.

**Цена решения, принятая осознанно:** иностранные почтовые сервисы — почта заметной доли
живых пользователей, отсечение срежет часть регистраций. У этих людей остаются входы через
Яндекс ID и VK ID, поэтому тупика не возникает; текст ошибки прямо предлагает этот путь.

## Безопасность

**Лимиты.** `src/lib/rate-limit.ts` расширяется: первый аргумент `checkLimit` становится
произвольным ключом (сейчас это `userId`), добавляются виды `login`, `register`, `reset`.

| действие | лимит | `gapMs` | ключ |
|---|---|---|---|
| вход | 10 за 15 мин | 0 | `email + ip` |
| регистрация | 5 в час | 5 с | `ip` |
| повторное письмо подтверждения | 5 в час | 60 с | `email`, плюс 10 в час на `ip` |
| запрос сброса | 3 в час | 60 с | `email`, плюс 10 в час на `ip` |

`gapMs` (минимальная пауза между попытками) задаётся явно для каждого вида: в текущем
`RULES` он обязателен, а для входа пауза не нужна — там работает счётчик попыток. Повторное
письмо и сброс ключуются в том числе по почте, иначе смена IP превращает форму в способ
завалить чужой ящик письмами.

**Откуда берётся IP.** Сейчас лимитер ключуется только на `userId`, извлечения IP в проекте
нет вообще. Добавляется `src/lib/http/client-ip.ts`: приложение работает за Caddy, который
дописывает реальный адрес пира в конец `X-Forwarded-For`, поэтому берётся **последний**
элемент заголовка, а не первый. Первый элемент подконтролен клиенту — доверие к нему сделало
бы лимиты на регистрацию и сброс обходимыми одной подделанной строкой, а на них держится
вся антиспам-модель. Если заголовка нет (локальный dev без прокси) — ключ `local`.

Лимитер в памяти; деплой одноинстансный, этого достаточно (в файле уже стоит TODO про
Redis при масштабировании).

**Тайминги.** При неизвестной почте выполняется проверка argon2 против фиктивного хэша,
ответ — тот же текст «Неверная почта или пароль». Без этого разница во времени ответа
выдаёт факт регистрации.

**Перечисление аккаунтов.** На сбросе ответ всегда одинаковый. На регистрации факт
существования аккаунта раскрывается осознанно — иначе нельзя подсказать «войдите через
Яндекс», и человек утыкается в стену.

**Правила пароля.** От 8 до 200 символов (верхняя граница — чтобы не грузить argon2
килобайтными строками), пароль не равен собственной почте. Словарь популярных паролей не
тащим.

**Нормализация почты.** `trim` + нижний регистр. Без этого `A@ya.ru` и `a@ya.ru` заведут
два аккаунта: `unique` в Postgres регистрозависим.

**Cookie сессии.** `httpOnly`, `sameSite=lax`, `secure` на https, имя — `__Secure-`-префикс
на https (логика уже есть в `sessionCookieName`).

**Токены.** 32 случайных байта из `crypto.randomBytes`, base64url; в БД только sha256;
одноразовые (`usedAt`); при выпуске нового токена того же назначения прежние удаляются.

**Чистка — ленивая.** Перед выпуском нового токена сносим просроченные и давно погашенные
записи этого юзера, по образцу `expireStaleRequests()` для заявок. Крон под это не заводим:
единственный планировщик в проекте — контейнер `backup`, который в 03:00 снимает дамп
(`scripts/backup-entrypoint.sh`), и он живёт только в проде, тогда как ленивая чистка
работает и в деве. Если объёмы когда-нибудь вырастут, `delete from email_tokens` можно
повесить на тот же ночной прогон — но не сейчас. Погашенные предъявлением токены держим 15
минут ради льготного окна. Побочный эффект принят: строки юзеров, которые больше никогда не
запросят новый токен, лениво не удаляются и лежат до ручной чистки.

## Письма

Транспорт — SMTP Яндекс 360 через `nodemailer`. Переменные окружения по правилу «все или ни
одной» (как `STORAGE_*` в `src/lib/env.ts`): `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`,
`SMTP_PASSWORD`, `SMTP_FROM`.

**Выбор транспорта** — по наличию `SMTP_*`: настроены → SMTP, пусты → консольный транспорт
(печатает получателя, тему и ссылку в stdout). Консольный транспорт доступен только при
`NODE_ENV !== "production"`; в проде отсутствие `SMTP_*` означает «транспорта нет».

**Что рендерится на `/login`:**

| режим | форма входа | регистрация и сброс |
|---|---|---|
| dev (транспорт консольный или SMTP) | есть | есть |
| prod, `SMTP_*` заданы | есть | есть |
| prod, `SMTP_*` пусты | есть | скрыты |

Вход не гейтится транспортом: проверка пароля письма не требует, а скрытие формы отрезало бы
от аккаунтов людей, которые уже завели пароль. Скрываются только те действия, которые без
письма не могут завершиться.

Гейт живёт не только в рендере: Server Actions регистрации и сброса сами проверяют
доступность транспорта и отказывают, если его нет. Иначе прямой вызов в обход UI завёл бы
аккаунт, который невозможно подтвердить.

Три письма (подтверждение регистрации, повторное подтверждение, сброс пароля). Тексты — в
`theme/content.ts` по конвенции проекта. В каждом: срок действия ссылки и строка «если это
были не вы — просто проигнорируйте письмо». Отправитель `noreply@<домен>`.

Отправка не блокирует ответ формы дольше разумного: ошибка SMTP логируется, юзеру
показывается «Не удалось отправить письмо, попробуйте позже» — аккаунт при этом остаётся
неподтверждённым и его можно дожать кнопкой «Отправить ещё раз».

## Тесты

Vitest, только в `tests/**`, импорт через `@/` (конвенция проекта). Ориентировочно 30
тестов.

**Как тестируем то, что ходит в БД.** Живой Postgres в тестах не поднимаем — в проекте его
нет, единственный тест с БД точечно мокает `getDb` (`tests/storage/upload-route.test.ts`).
Поэтому вся логика этой фичи пишется чистыми функциями поверх узкого порта данных
(`findUserByEmail`, `createUser`, `setPassword`, `issueToken`, `consumeToken`,
`dropSessions`, …), а сценарные тесты гоняют их на реализации порта в памяти. Реальный
drizzle-адаптер порта покрывается только ручной проверкой. Это влияет на структуру кода,
поэтому решение зафиксировано здесь, а не оставлено планировщику.

Список:

- нормализация почты; стоп-лист (встроенный + из env; поддомены; регистр)
- правила пароля; argon2 round-trip; фиктивная проверка не бросает
- токены: погашение, протухание, повторное использование, чужой токен, гашение прежних при
  выпуске нового
- регистрация → подтверждение → вход (полный путь)
- вход с неподтверждённой почтой запрещён
- повторная регистрация на неподтверждённую почту перезаписывает пароль
- регистрация на почту OAuth-юзера отклоняется с нужным кодом (дискриминатор — `accounts`,
  а не `emailVerified`)
- вход в аккаунт без `passwordHash` даёт подсказку про OAuth, а не «неверный пароль»
- сброс удаляет все сессии юзера; сброс не выпускается ни для OAuth-юзера без пароля, ни
  для неподтверждённого аккаунта
- VK-флоу не склеивает по e-mail: коллизия даёт `email_taken`, а найденный по `accounts`
  юзер по-прежнему входит
- льготное окно: повторный переход по свежепогашенному `verify`-токену выдаёт сессию, за
  пределами окна — отказ
- `client-ip`: берётся последний элемент `X-Forwarded-For`, подделанный первый игнорируется
- лимиты: превышение возвращает `retryAfterSec`

Письма — фейковый транспорт, живой SMTP в тестах не трогаем.

## Ручная проверка после реализации

1. `docker compose up -d db` → `pnpm db:migrate` → `pnpm dev` без `SMTP_*`: форма почты на
   `/login` есть, письма печатаются в консоль, кнопки провайдеров на месте.
2. Регистрация → письмо в консоли → переход по ссылке → `/welcome` → выбор `username` →
   главная.
3. Повторный вход по паролю; вход с неверным паролем; вход до подтверждения.
4. Сброс пароля из второй вкладки: старая сессия перестаёт работать после смены.
5. Регистрация с `gmail.com`: красная строка под полем сразу после ввода почты.
6. Регистрация на почту, уже заведённую через Яндекс: подсказка войти через Яндекс.
7. Тёмная и светлая темы, мобильная ширина без горизонтального скролла.
8. `pnpm build` + запуск docker-образа: `@node-rs/argon2` — нативный модуль, а сборка идёт
   на `node:20-alpine` с `output: "standalone"`. Прецедент `sharp` показывает, что
   трассировка зависимостей обычно справляется, но проверить, что контейнер стартует и
   регистрация в нём проходит, надо отдельно.
