# prokat — вход и регистрация по почте с паролем

Дата: 2026-08-11
Статус: согласовано в брейнсторме, ожидает вычитки

## Контекст и цель

Сейчас в проект можно попасть только через OAuth: Яндекс ID (штатный провайдер Auth.js)
и VK ID (собственный OAuth 2.1 + PKCE в `src/lib/auth/oauth-vk.ts`). Человек без аккаунта
в этих сервисах — или не желающий ими светить — зарегистрироваться не может.

Цель: добавить третий способ входа — **почта + пароль** — не ломая два существующих.

## Ключевые решения

1. **Пароль, а не магик-линк.** Повторный вход мгновенный, без письма.
2. **Подтверждение почты обязательно до первого входа.** Незаподтверждённый аккаунт войти
   не может.
3. **Автосклейки с OAuth нет.** Совпадение почты — понятный отказ с подсказкой, каким
   способом входить. Привязка второго способа из профиля — отдельная задача, не здесь.
4. **Сессию выдаём сами, database-стратегия остаётся.** Credentials-провайдер Auth.js не
   используется.
5. **Стоп-лист почтовых доменов** с проверкой на сервере; юзеру сообщается конкретная
   причина, но только после ввода почты.
6. **Фича выключена, пока не настроен SMTP** — как сейчас выключены провайдеры без ключей.

Сознательно **не** делаем сейчас (YAGNI): экран «Способы входа» в профиле (задать пароль
для OAuth-аккаунта, привязать/отвязать провайдера), смену почты, магик-линк, OTP-коды,
двухфакторную аутентификацию, словарь скомпрометированных паролей, капчу.

## Почему не Credentials-провайдер Auth.js

`session.strategy` в проекте — `"database"` (`src/lib/auth/config.edge.ts`). Это значит,
что сессия — строка в таблице `sessions`, а cookie хранит только её токен. На этом стоит
весь проект: VK-флоу пишет сессию в БД напрямую (`upsertUserAndSession`), `session`-коллбэк
берёт поля из `user`, отданного адаптером, а бан действует мгновенно — достаточно удалить
строку сессии.

`CredentialsProvider` требует `strategy: "jwt"`. Переход на JWT означал бы переписывание
VK-флоу и `session`-коллбэка, а забаненный юзер продолжал бы работать до истечения токена.
Цена несопоставима с выгодой.

Поэтому вход по паролю повторяет уже работающий в проекте паттерн: проверили пароль →
вставили строку в `sessions` → поставили cookie. Тот же механизм, другая проверка на входе.

Отвергнутый третий вариант — Credentials-провайдер с ручной подменой cookie на
database-токен внутри коллбэков — опирается на недокументированное поведение беты
`next-auth` и ломается при обновлении.

## Данные

### Изменения схемы (`drizzle/schema.ts`)

**`users` — новая колонка:**

| поле | тип | смысл |
|---|---|---|
| `passwordHash` | `text`, nullable | argon2id-хэш. У OAuth-юзеров NULL |

Отдельная таблица не нужна: связь строго 1:1. Существующая колонка `emailVerified`
(`timestamp`, сейчас всегда NULL) начинает использоваться по назначению — это признак
«почта подтверждена, аккаунт живой».

**`email_tokens` — новая таблица** (одноразовые ссылки из писем):

| поле | тип | смысл |
|---|---|---|
| `id` | `text` PK | ULID |
| `userId` | `text` → `users.id`, `on delete cascade` | чей токен |
| `purpose` | enum `verify` / `reset` | тип ссылки |
| `tokenHash` | `text`, uniq | sha256 от токена из письма |
| `expiresAt` | `timestamp` | 24 ч для `verify`, 1 ч для `reset` |
| `usedAt` | `timestamp`, nullable | штамп погашения; повторный клик не сработает |
| `createdAt` | `timestamp` | для чистки протухших |

Индекс по (`userId`, `purpose`) — нужен, чтобы гасить прежние токены при выпуске нового.

**Почему хэш, а не сам токен.** Строка из письма — это одноразовый пароль. Дамп БД (в том
числе бэкап, уезжающий в S3) с сырыми токенами даёт вход в чужие аккаунты. В письмо уходит
оригинал, в БД лежит sha256 — сверяем при клике. Соль не нужна: токен и так 32 случайных
байта, перебор бессмысленен.

**Почему не переиспользуем `verification_tokens`.** Это таблица Auth.js: составной ключ
(`identifier`, `token`), нет ни `purpose`, ни `usedAt`. Свои данные в ней конфликтуют с
адаптером, если позже появится магик-линк.

Миграция генерируется через `pnpm db:generate`, ломающих изменений нет: существующие юзеры
получают `password_hash = NULL`.

### Хэширование пароля

`argon2id` через `@node-rs/argon2` (нативный, без сборки из исходников). Параметры — дефолт
библиотеки (OWASP-совместимый): 19 МиБ памяти, 2 итерации, параллелизм 1.

bcrypt отвергнут: лимит 72 байта на пароль (длинные парольные фразы молча обрезаются) и
слабее против перебора на GPU.

## Пользовательские флоу

### Регистрация

1. `/login`, форма «Почта и пароль» под кнопками провайдеров: почта, пароль, повтор пароля.
2. Сервер нормализует почту, проверяет стоп-лист доменов, правила пароля, лимиты.
3. Создаётся `users` с `emailVerified = NULL`, `passwordHash`, без `username`.
4. Выпускается токен `verify`, письмо уходит на почту.
5. Юзера **не** логиним — показываем «Письмо отправлено на a@ya.ru» и кнопку «Отправить ещё
   раз» (под лимитом).

### Подтверждение почты

Ссылка ведёт на `GET /api/auth/email/verify?token=…`:

1. Токен ищется по sha256, проверяется `purpose`, `expiresAt`, `usedAt`.
2. Стоп-лист проверяется повторно — домен мог попасть в список после регистрации.
3. `emailVerified = now()`, `usedAt = now()`.
4. Выдаётся сессия, редирект на `/welcome` выбирать `username` — тот же онбординг, что
   после OAuth (`requireAuthState` всё равно увёл бы туда).

Невалидный/протухший токен → `/login?error=verify_token_invalid` с предложением
зарегистрироваться заново или запросить письмо.

### Вход

1. Та же форма, режим «Войти».
2. Юзер ищется по нормализованной почте.
3. Проверка `passwordHash`; при отсутствии юзера выполняется фиктивная проверка argon2
   (см. «Тайминги»).
4. `emailVerified = NULL` → отказ с предложением отправить письмо повторно.
5. Успех → строка в `sessions` + cookie → редирект на `callbackUrl` (по умолчанию `/`).

Забаненный юзер входит штатно: сессия выдаётся, `requireAuthState` уводит на `/banned` —
так же, как с VK и Яндексом. Одна дорога вместо двух.

### Сброс пароля

1. `/login` → «Забыли пароль?» → форма с почтой.
2. Ответ всегда одинаковый: «Если такая почта зарегистрирована — письмо отправлено».
3. Если юзер существует и у него есть `passwordHash` — выпускается токен `reset` (1 час),
   прежние неиспользованные `reset`-токены этого юзера гасятся.
4. Ссылка ведёт на `/reset?token=…` — форма нового пароля; токен проверяется и при
   отрисовке страницы, и при отправке.
5. Успех: новый `passwordHash`, `usedAt`, **удаление всех строк `sessions` этого юзера** и
   всех его непогашенных `reset`-токенов, затем выдача новой сессии и редирект на `/`.

Удаление сессий обязательно: сброс — это в том числе реакция на угон, злоумышленник с
активной cookie должен потерять доступ немедленно.

У OAuth-юзера без `passwordHash` сброс не выпускает токен (ответ тот же, письма нет) —
иначе через «забыли пароль» можно было бы завести пароль к чужому OAuth-аккаунту.

### Коллизии почты с OAuth

| ситуация | поведение |
|---|---|
| Регистрация паролем, почта уже у OAuth-юзера | «Эта почта уже привязана ко входу через Яндекс/VK — войдите этим способом» |
| Регистрация паролем, почта занята **неподтверждённым** аккаунтом | Разрешаем: перезаписываем `passwordHash`, гасим прежние `verify`-токены, шлём новое письмо |
| Вход через Яндекс, почта уже у password-юзера | Auth.js отдаёт `OAuthAccountNotLinked`; ловим на `/login` и показываем «У этой почты уже есть вход по паролю» |

Перезапись неподтверждённого аккаунта нужна, чтобы нельзя было «застолбить» чужой адрес:
иначе владелец почты никогда не зарегистрируется. Безопасно, потому что доступ получит
только тот, кто откроет письмо.

VK-юзеры без почты получают заглушку `vk-<id>@vk.placeholder` и в коллизии не участвуют —
такой домен в почте не встречается.

## Стоп-лист почтовых доменов

Список живёт в `src/lib/auth/blocked-email-domains.ts`, стартовое содержимое — `gmail.com`.
Расширяется двумя путями:

- правкой файла (требует пересборки);
- переменной `BLOCKED_EMAIL_DOMAINS=foo.com,bar.com` — значения добавляются к встроенному
  списку, домен закрывается рестартом контейнера.

Сравнение по домену в нижнем регистре после нормализации почты.

**Где проверяется:** при регистрации, при подтверждении почты и при запросе сброса — иначе
домен, добавленный позже, остался бы рабочим для уже заведённых аккаунтов. Вход
существующих юзеров не блокируем: отсечение на входе превратило бы стоп-лист в способ
внезапно потерять аккаунт.

**Как сообщаем.** Заранее в форме ничего не пишем. Как только человек ушёл из поля почты,
форма дёргает Server Action `checkEmailDomain`, и под полем появляется красная строка
«Регистрация с почт gmail.com не поддерживается». Список при этом не уезжает в браузерный
бандл. Серверная проверка при отправке формы остаётся источником истины.

**Известный компромисс:** `gmail.com` — почта заметной доли живых пользователей, отсечение
срежет часть регистраций. Если цель — одноразовые ящики, список стоит переориентировать на
disposable-домены. Механизм от содержимого списка не зависит.

## Безопасность

**Лимиты.** `src/lib/rate-limit.ts` расширяется: первый аргумент `checkLimit` становится
произвольным ключом (сейчас это `userId`), добавляются виды `login`, `register`, `reset`.

| действие | лимит | ключ |
|---|---|---|
| вход | 10 за 15 мин | `email + ip` |
| регистрация, повторное письмо | 5 в час | `ip` |
| запрос сброса | 3 в час | `email`, плюс 10 в час на `ip` |

Лимитер в памяти; деплой одноинстансный, этого достаточно (в файле уже стоит TODO про
Redis при масштабировании).

**Тайминги.** При неизвестной почте выполняется проверка argon2 против фиктивного хэша,
ответ — тот же текст «Неверная почта или пароль». Без этого разница во времени ответа
выдаёт факт регистрации.

**Перечисление аккаунтов.** На сбросе ответ всегда одинаковый. На регистрации факт
существования аккаунта раскрывается осознанно — иначе нельзя подсказать «войдите через
Яндекс», и человек утыкается в стену.

**Правила пароля.** От 8 до 200 символов (верхняя граница — чтобы не грузить argon2
килобайтными строками), пароль не равен собственной почте. Словарь популярных паролей не
тащим.

**Нормализация почты.** `trim` + нижний регистр. Без этого `A@ya.ru` и `a@ya.ru` заведут
два аккаунта: `unique` в Postgres регистрозависим.

**Cookie сессии.** `httpOnly`, `sameSite=lax`, `secure` на https, имя — `__Secure-`-префикс
на https (логика уже есть в `sessionCookieName`).

**Токены.** 32 случайных байта из `crypto.randomBytes`, base64url; в БД только sha256;
одноразовые (`usedAt`); при выпуске нового токена того же назначения прежние гасятся.

## Письма

Транспорт — SMTP Яндекс 360 через `nodemailer`. Переменные окружения по правилу «все или ни
одной» (как `STORAGE_*` в `src/lib/env.ts`): `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`,
`SMTP_PASSWORD`, `SMTP_FROM`.

Если SMTP не настроен — форма почты на `/login` не рендерится, ровно как сейчас не
рендерятся кнопки провайдеров без ключей. В dev это даёт безопасное поведение: письма
печатаются в консоль вместо отправки.

Три письма (подтверждение регистрации, повторное подтверждение, сброс пароля). Тексты — в
`theme/content.ts` по конвенции проекта. В каждом: срок действия ссылки и строка «если это
были не вы — просто проигнорируйте письмо». Отправитель `noreply@<домен>`.

Отправка не блокирует ответ формы дольше разумного: ошибка SMTP логируется, юзеру
показывается «Не удалось отправить письмо, попробуйте позже» — аккаунт при этом остаётся
неподтверждённым и его можно дожать кнопкой «Отправить ещё раз».

## Тесты

Vitest, только в `tests/**`, импорт через `@/` (конвенция проекта). Ориентировочно 30
тестов:

- нормализация почты; стоп-лист (встроенный + из env; поддомены; регистр)
- правила пароля; argon2 round-trip; фиктивная проверка не бросает
- токены: погашение, протухание, повторное использование, чужой токен, гашение прежних при
  выпуске нового
- регистрация → подтверждение → вход (полный путь)
- вход с неподтверждённой почтой запрещён
- повторная регистрация на неподтверждённую почту перезаписывает пароль
- регистрация на почту OAuth-юзера отклоняется с нужным кодом
- сброс удаляет все сессии юзера; сброс для OAuth-юзера без пароля не выпускает токен
- лимиты: превышение возвращает `retryAfterSec`

Письма — фейковый транспорт, живой SMTP в тестах не трогаем.

## Ручная проверка после реализации

1. `docker compose up -d db` → `pnpm db:migrate` → `pnpm dev` без `SMTP_*`: формы почты на
   `/login` нет, кнопки провайдеров на месте.
2. С `SMTP_*` из dev-заглушки: регистрация → письмо в консоли → переход по ссылке →
   `/welcome` → выбор `username` → главная.
3. Повторный вход по паролю; вход с неверным паролем; вход до подтверждения.
4. Сброс пароля из второй вкладки: старая сессия перестаёт работать после смены.
5. Регистрация с `gmail.com`: красная строка под полем сразу после ввода почты.
6. Регистрация на почту, уже заведённую через Яндекс: подсказка войти через Яндекс.
7. Тёмная и светлая темы, мобильная ширина без горизонтального скролла.
