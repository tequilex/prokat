# prokat — C2C-модель данных (актуальный спек)

Дата: 2026-07-20
Статус: согласовано в брейнсторме, ожидает вычитки

Заменяет прежний спек редизайна (2026-07-19, удалён). Действующие визуальные и
адаптивные правила из него перенесены в конец этого документа.

## Контекст и цель

prokat — P2P-маркетплейс аренды вещей («Авито для аренды»), форк контентного skelet.
UI-редизайн (навигация, визуальный язык, страницы — фазы 1–5) закрыт в master.

Осталась доменная модель. Сейчас она построена вокруг сущности **`providers`** (профиль
проката): товары (`listings`) привязаны к провайдеру, а не к юзеру, и кабинет заперт за
барьером «сначала создай прокат». При этом провайдер уже фактически 1:1 с юзером — то
есть это пустая прослойка, дающая ту самую «неразбериху providers/users».

Цель: **убрать прослойку `providers`. Модель — просто `users`: каждый юзер и арендует, и
сдаёт** (товар принадлежит юзеру напрямую). Это финализирует вопрос модели данных,
который прежний спек оставлял открытым (варианты A/B/C), в пользу полного удаления
`providers` — оправданно, т.к. БД тестовая и сносится целиком, а минусы этого варианта
(ломает миграции/слаги/SEO) при сносе неактуальны.

## Ключевые решения (брейнсторм 2026-07-20)

1. **Данные:** старую БД сносим, схему переписываем начисто, свежий seed. История
   миграций обнуляется (свежая стартовая вместо 0000–0002).
2. **URL товара:** `/{city}/{category}/{slug}-{id}` (Авито-стиль, id в хвосте).
3. **Контакты/место:** минимум — телефон продавца из `users.phone`, город у товара
   (`listings.cityId`), опциональный район текстом. `address/phones[]/workHours/lat-lon`
   уходят.
4. **Модерация:** без премодерации, товар публикуется сразу `active`.
5. **username:** остаётся как есть (ручной выбор на `/welcome`); профиль — `/u/{username}`.
6. **Верификация:** переезжает с провайдера на юзера, ставится вручную админом.
7. **Профиль и настройки:** сливаются в один экран.

Сознательно **не** делаем сейчас (YAGNI): рейтинги/отзывы, монетизацию
(тарифы/подписки/промо), премодерацию, СМС/документ-верификацию, жалобы, мультигород у
одного товара, чат.

## Модель данных

Итог: 15 таблиц → 12. Удаляются `providers`, `subscriptions`, `promotions` и enum
`provider_plan`. Связь становится плоской: **`users → listings → booking_requests`**;
город и категория — атрибуты товара.

### `users` — ядро, добавляется верификация

Без изменений: `id`, `email`, `emailVerified`, **`username`** (по-прежнему nullable +
unique, заполняется через `/welcome`), `name`, `phone`, `phoneVerifiedAt`, `image`,
`bio`, `role`, `createdAt`, `banReason`, `bannedAt`.

Добавляется:
- `isVerified boolean NOT NULL DEFAULT false` — «проверенный продавец».
- `verifiedAt timestamp` (nullable) — когда отмечен.

### `listings` — товар принадлежит юзеру

| Поле | Было | Стало |
|------|------|-------|
| владелец | `providerId → providers` | **`ownerUserId → users`** (onDelete cascade) |
| город | (на провайдере) | **`cityId → cities` NOT NULL** (новое) |
| место | — | **`location varchar(120)` nullable** — район/ориентир (новое, опц.) |
| slug | `varchar(80)`, uniq в пределах провайдера | `varchar(80)` NOT NULL, **без уникального индекса** (уникальность URL даёт `id`) |
| статус | active/hidden/archived/**on_moderation** | active/hidden/archived, default **active** (`on_moderation` убран из enum) |

Без изменений: `categoryId`, `title`, `description`, `priceDay/Hour/Week`,
`depositAmount`, `depositType`, `quantity`, `photosJson`, `createdAt`, `updatedAt`.

Индексы:
- `listings_city_category_status_idx` на `(cityId, categoryId, status)` — списки каталога.
- `listings_owner_idx` на `(ownerUserId)` — «мои объявления».
- Удаляются старые `providers_city_slug_uq`-зависимый `providerSlugUq`, `providerIdx`.

### `booking_requests` — заявка без провайдера

- `providerId → providers` заменяется на **`ownerUserId → users`** (владелец товара).
  Это осознанная денормализация ради индекса «входящие заявки владельцу» без join'а к
  `listings`; проставляется при создании заявки из `listing.ownerUserId` (владелец
  неизменен — рассинхрона нет).
- `providerComment` → **`ownerComment`**.

Без изменений: `listingId`, `customerUserId`, `dateFrom/To`, `qty`, `status`,
`customerPhone`, `customerComment`, `createdAt`, `respondedAt`, `expiresAt`.

Индексы: `booking_requests_owner_status_idx` на `(ownerUserId, status, createdAt)`;
`customerIdx`; `listingIdx`.

### Без изменений

`availability`, `cities`, `categories`, `events`, `uploads`, `accounts`, `sessions`,
`verification_tokens`.

## URL и резолвинг

```
/{city}                             → витрина города
/{city}/{category}                  → список товаров корневой категории (+подкатегории роллапом)
/{city}/{category}/{sub}            → список подкатегории
/{city}/{categorySlug}/{slug}-{id}  → карточка товара
/u/{username}                       → профиль продавца
```

Слаг категории уникален глобально (уже так в схеме), поэтому карточка товара **всегда 3
сегмента**: `город / слаг-непосредственной-категории-товара / slug-id`, независимо от
уровня категории. Третий сегмент резолвится так:

- извлечь `id` из хвоста (`…-{id}`; `id` — ULID без дефисов → часть после последнего `-`);
- если активный товар с таким `id` есть — это карточка; при несовпадении слага
  категории/товара в URL с актуальными — 301 на канонический URL;
- иначе — трактуем пару как «категория + подкатегория» (список).

Резолвер `resolveCitySegment` переписывается с «категория | провайдер» на «категория», а
разбор третьего сегмента («подкатегория | товар») живёт в `[city]/[seg]/[sub]`.

## Профиль продавца `/u/{username}`

Новый публичный роут. Показывает: имя + аватар (из VK), `bio`, «на сайте с
`{createdAt}`», значок «проверен» (`isVerified`), сетку активных товаров продавца. Без
рейтинга и отзывов. `/u/` уже в `RESERVED_USERNAMES` — конфликтов ников не будет.

## Кабинет `/cabinet/*`

- **Гейт:** `requireOwner` (наличие провайдера) удаляется; доступ — любой залогиненный
  юзер с ником (`requireAuthState`). Барьера «создай прокат» нет.
- Удаляются: `createProvider`/`updateProvider`, компонент `ProviderForm`, схема
  `providerFormSchema`, роут `/cabinet/new`.
- `/cabinet` → «Мои объявления» (список товаров юзера).
- **Форма товара** (`ListingForm`) получает поля **город** (select из `cities`) и
  **`location`** (опц.); категория уже есть. Публикация сразу `active`.
- `/cabinet/settings` + `/(me)/profile` сливаются в **один экран настроек профиля**
  (`name`, `bio`, avatar, `phone`). Публичный профиль — отдельно на `/u/{username}`.
- `/cabinet/requests` (входящие по `ownerUserId`), `/cabinet/calendar` — остаются.
- Серверный слой `owner.ts`/actions переписывается с `providerId` на `userId`.

## Админка `/admin/*`

- Удаляется раздел **providers** и вся верификация прокатов.
- `/admin/users` — добавляется действие **verify/unverify** юзера (server action
  переключает `isVerified`/`verifiedAt`).
- `/admin/listings` — показывает владельца (`name`/`username`) вместо проката.
- `/admin/requests` — по `ownerUserId`.
- Остаются: `cities`, `categories` (справочники), `users` (бан + верификация),
  `listings`, `requests`.

## Изменения по слоям кода (обзор, не план реализации)

- **Схема/миграции/seed:** переписать `drizzle/schema.ts`; обнулить `drizzle/migrations`
  и сгенерировать свежую; переписать `scripts/seed.ts` под новую модель.
- **`catalog.ts`:** убрать join к `providers`; фильтр по `listings.cityId`; новый
  резолвинг сегмента/товара; `getListingBySlug` → по `id`.
- **`owner.ts` + `actions/owner.ts`:** гейт по юзеру; удалить провайдер-функции; listing
  по `ownerUserId`; `createListing` принимает `cityId`/`location`.
- **`booking.ts` + `actions/booking.ts`:** заявка по `ownerUserId`; `ownerComment`.
- **`me.ts`, `admin.ts`, `actions/admin.ts`:** убрать провайдерные части; verify-действие.
- **Публичные страницы:** новый резолв в `[city]/[seg]/[sub]`; новый `/u/[username]`.
- **Кабинет:** убрать `/cabinet/new` и `ProviderForm`; поля города в форме товара; единый
  экран настроек.
- **Компоненты:** `ListingCard` (подпись продавца), `OwnerCard`/`BookingWidget` (контакт
  из `users`), удалить `ProviderForm`.
- **SEO:** `jsonld`, `sitemap`, `catalog/format` — по товару/категории/продавцу.
- **`lib/owner/validation.ts`:** убрать `providerFormSchema`; в `listingFormSchema` +`cityId`.
- **Тесты:** обновить под новую модель.

# Действующие сквозные правила (перенесены из редизайна)

Применяются ко всей работе — и к этой, и к будущей.

## Визуальный язык

Ориентиры: чистота и воздух **Apple** + ясная функциональная структура и заметная цена
**Ozon/Avito**.

- Много воздуха, крупная плотная типографика (system / SF-подобный шрифт, отрицательный
  трекинг на заголовках).
- Мягкие тени; скругления 16–20px у карточек и крупных блоков, 10–12px у контролов.
- Спокойная нейтральная палитра (белый фон, серии серых), один уверенный акцент.
- **Акцент — зелёный (Avito-подобный, `#04b26a`)** для CTA, цены, активных состояний.
- Токены живут в `theme/tokens.css`; не хардкодить цвета в компонентах.
- Полировка/анимации по принципам emil-design-eng: ease-out, длительности <300ms для UI,
  `scale(0.97)` на нажатие, origin-aware поповеры (уровень реализации, не спеки).

## Темы (светлая и тёмная) — обязательны

- Обе темы поддерживаются на **всех** экранах; ничего не остаётся «только светлым».
- Всё через токены в `theme/tokens.css` (`:root` + `.dark`), без хардкода. Зелёный акцент
  подбирается отдельно для тёмной темы (чуть светлее/насыщеннее для контраста).
- Проверять контраст текста/цены/бейджей в обеих темах; тени в тёмной — мягче или
  заменяются бордером/приподнятым фоном.
- Переключатель темы — `next-themes`.

## Мобайл-адаптив — первого класса

Каждый экран проектируется так, чтобы на телефоне выглядел адекватно, а не как «сжатый
десктоп».

- **Шапка:** сворачивается — поиск крупной строкой/иконкой, город и профиль компактны,
  «Разместить» доступна.
- **Каталог:** дерево подкатегорий и фильтры — через bottom-sheet/панель, а не постоянно;
  карточки — сетка 2 колонки, тап-цели ≥44px.
- **Объявление:** липкая карточка брони → фиксированная нижняя панель (цена +
  «Забронировать»); выбор дат/календарь — в bottom-sheet.
- **Главная:** герой и плитка категорий в одну колонку, крупный поиск.
- **Кабинет:** вкладки верхними табами/свайпаемой полосой, а не боковым сайдбаром.
- Никакого горизонтального скролла body; широкие элементы (таблицы, календарь) скроллятся
  внутри своих контейнеров; жесты и нижние панели — с оглядкой на safe-area.

## Открытые вопросы для этапа планирования

- Стратегия миграций: свежая стартовая vs накат поверх (предлагается свежая — БД сносится).
- Канонизация URL товара (301 при устаревшем слаге категории/товара в адресе).
- Дефолтный город в форме товара (последний выбранный / из профиля) — UX-деталь.
- Сверка с фактическим состоянием кабинета и зоны `(me)` после фаз 1–5 при планировании.
