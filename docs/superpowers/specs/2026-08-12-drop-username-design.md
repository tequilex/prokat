# prokat — отказ от ника: профиль по id, имя вместо ника

Дата: 2026-08-12
Статус: согласовано в брейнсторме, ожидает вычитки

## Контекст и цель

Сейчас новый пользователь после регистрации любым способом упирается в экран
`/welcome` и обязан придумать `username`. Это барьер на самом дорогом участке
воронки: человек шёл бронировать вещь, а вместо брони придумывает ник.

Проверка кода показала, что ник почти никому не нужен:

- бронь его не требует — `createBookingRequest` смотрит только `session.user.id`;
- в SEO и sitemap он не участвует;
- он нужен ровно для одного: адрес публичной витрины `/u/{username}` и подпись
  у аватара.

При этом ник уводит на `/welcome` из трёх мест: роут подтверждения почты (всегда),
страница `/login` для залогиненного без ника, и гард `requireAuthState` на
кабинете, профиле и «Моих заявках». На мобиле три вкладки из пяти ведут в эти
разделы, поэтому упереться в барьер можно сразу после входа.

Цель: **убрать `username` из системы целиком.** Публичный профиль адресуется по
ULID, человека представляет `name`.

## Ключевые решения

1. **Профиль по id: `/u/{id}`.** Ни ника, ни слага из имени.
2. **Имя обязательно при регистрации почтой** — отдельным полем в той же форме,
   без дополнительного экрана. У OAuth имя приезжает от провайдера.
3. **`/welcome` удаляется**, вместе с `validateUsername` и колонкой `username`.
4. **Подтверждение почты возвращает туда, откуда пришли**, а не на `/welcome`.
5. **Переходного периода нет** — живых пользователей и проиндексированных
   адресов `/u/{ник}` не существует (подтверждено владельцем проекта).

Сознательно **не** делаем: слаг из имени в адресе, автогенерацию ника,
отображение почты как имени, «красивые» адреса витрин.

## Почему id, а не слаг из имени

Слаг вида `/u/ivan-petrov-01j8f3…` (как у карточек товара) выглядел бы уместнее,
но у него две проблемы.

**Имя в адресе — это разглашение.** Адрес уезжает в историю браузера, в чужие
мессенджеры, в реферер и в поисковую выдачу. Продавец здесь — частное лицо,
сдающее дрель соседу; он вводил имя для подписи под объявлением, а не для
публикации в URL. Авито поступает так же: у частника профиль по непрозрачному
идентификатору (`/user/a93446d8…/profile`), читаемые адреса — только у
компаний-брендов.

**Имя из OAuth — не то имя, которым человек хочет представляться.** Яндекс отдаёт
`display_name`, и у части людей это логин вида `vasya-pupkin-1990`. Человек,
который хочет быть «ПрокатМастер», получил бы адрес с чужим для него именем.

Адрес по id снимает оба вопроса и заодно убирает уникальность, коллизии и
зарезервированные слова.

## Данные

### `users`

| Изменение | Смысл |
|---|---|
| удалить колонку `username` | больше не используется |
| удалить индекс `users_username_idx` | вместе с колонкой |

`name` остаётся `varchar(100)`, nullable — у OAuth-юзеров он заполнен провайдером,
у регистрирующихся почтой станет обязательным на форме (валидация на уровне
приложения, не БД: у старых записей имени может не быть).

Миграция генерируется `pnpm db:generate`; данные ников теряются осознанно.

## Регистрация и вход

**Форма регистрации почтой** получает поле «Имя» рядом с почтой и паролем:
обязательное, 1–100 символов после `trim`. Отдельного шага нет.

**OAuth** не меняется: VK отдаёт имя и фамилию (в VK они обязательны), Яндекс —
`display_name ?? real_name ?? first_name`, то есть пусто не бывает.

**Подтверждение почты** перестаёт вести на `/welcome`. Ссылка в письме несёт
адрес возврата, роут пропускает его через `safeCallback` (только относительные
пути) и редиректит туда. Механизм тот же, что уже работает у входа по паролю.
Сценарий «бронировал → зарегистрировался → подтвердил почту → вернулся на тот же
товар с выбранными датами» закрывается целиком.

**Гард `requireAuthState`** перестаёт проверять ник и остаётся проверкой
«залогинен и не забанен». Кабинет, профиль и «Мои заявки» открываются сразу.

**Страница `/login`** для залогиненного редиректит на `/` вместо `/welcome`.

## Профиль и вёрстка

| Место | Было | Стало |
|---|---|---|
| роут профиля | `/u/[username]` | `/u/[id]` |
| резолвер | `getSellerByUsername` | поиск по `users.id` |
| ссылка на продавца | из ника, с запасным вариантом по id | всегда `/u/{id}` |
| аватар-заглушка | буква и цвет из `username ?? name` | из `name`; без имени — нейтральная |
| меню пользователя | `@ник` строкой | имя, ниже почта |
| шапка и таб-бар | «Выбери ник» вместо меню | обычное меню с аватаром |
| админка | колонка «ник» | колонка «почта» |
| IndexNow | пинг `/u/{ник}` | пинг `/u/{id}` |

**Форма размещения** получает поле «Как вас увидят покупатели», предзаполненное
текущим `name`. Это единственное место, где человек осознанно решает, под каким
именем торговать: Вася Пупкин видит подставленное имя из Яндекса и может заменить
его на «ПрокатМастер», не догадываясь идти в профиль. Поле правит тот же
`users.name`.

Если имени нет (старые записи), карточка показывает «Продавец» — запасной вариант
уже реализован.

## Тесты

Правятся: схемный тест (нет колонки), четыре компонентных теста с пропом
`username`, тест IndexNow.

Добавляются:

- регистрация почтой без имени отклоняется, с именем — создаёт юзера с этим именем
- подтверждение почты редиректит на адрес из ссылки, а не на `/welcome`
- подделанный адрес возврата (`https://evil.com`) заменяется на `/`
- профиль резолвится по id; несуществующий id — 404
- заявка от юзера без имени показывает владельцу «Продавец»
- гард пускает залогиненного без имени в кабинет и профиль

## Ручная проверка

1. Регистрация почтой из модалки на карточке товара → письмо → переход по ссылке →
   возврат на тот же товар с выбранными датами → бронь проходит.
2. Вход через Яндекс → сразу главная, экрана выбора ника нет.
3. Кабинет, профиль и «Мои заявки» открываются без имени и без ника.
4. Публикация товара: поле имени предзаполнено, замена на «ПрокатМастер» меняет
   подпись на карточке и в блоке продавца.
5. Ссылка на продавца с карточки ведёт на `/u/{id}` и открывает витрину.
6. Тёмная и светлая темы, мобильная ширина без горизонтального скролла.
